Tabs, Cognitive Load, and the SPA I Didn't Build

My market report was over a thousand lines and one section ate 80% of the scroll. Here's how I cut the noise without reaching for React.

#ux#static-html#dashboards#financial-agent#mobile#cursor

My financial markets report started as a learning project. It turned into something I open almost every day. That shift came with a problem: the page was honest — every signal, methodology block, and disclaimer mattered — but honesty at full volume is hard to read on a phone.

One section, Opportunities, was roughly 900 lines out of ~1,120 on the page. Eighteen cards with the same skeleton repeated. The data was useful; the layout was exhausting.

The question that almost sent me down the wrong road

Before I changed a line of HTML, I asked the obvious senior-engineer question: should this become a multi-tabbed SPA (single-page app with client-side routing, component model, the whole npm universe)?

The honest tradeoff map looked like this:

  • What a SPA buys you: deep links, reusable components, sortable tables, animations, a path toward offline/PWA behavior.
  • What it does not buy you: fresher market data. The numbers still come from a Python job in CI. A React shell does not make FRED update faster.
  • What it costs: a build step, dozens of dependencies, ongoing upgrades, and days of scaffolding versus hours for targeted HTML/JS surgery.

I chose the boring path: ship lightweight tabs now, park a future SPA migration on the backlog, and only revisit it if real users ask for interactions the static page cannot support.

That decision is less about “hating frameworks” and more about founder discipline: validate that navigation and progressive disclosure solve the problem before you pay framework tax.

Six principles I am stealing for every data-heavy page

This work pulled together ideas from Bloomberg-style terminal UX, dashboard research, and staring at my own report until my eyes hurt. Six principles survived the edit:

  1. Data first, explanation second. When you open a section, you should see the chart or table immediately. Methodology belongs in a nested disclosure — not because it is unimportant, but because it is not why someone opened the section first.

  2. Two layers of progressive disclosure. Collapsing whole sections is layer one. Collapsing explanation inside a section is layer two. One layer was not enough for a page this dense.

  3. The five-second rule. A collapsed page should still communicate risk posture and direction. Scannable headers with numbers beat poetic titles. "Historical Parallels — base case -18.5%" tells a story; "Historical Parallels" does not.

  4. Find the monster section. If one block dominates scroll height, that is where you earn the win. Converting eighteen full cards into compact expandable rows was the single biggest reduction in perceived length — without deleting a single field of data.

  5. Mobile tab isolation, desktop scroll-through. Below 768px, only the active tab panel is visible. At desktop widths, panels stay in flow so power users can skim vertically. Same HTML, ~50 lines of vanilla JS, zero new dependencies.

  6. Hide, do not delete. Everything is still there — methodology, sources, disclaimers — just not in the first paint of every scroll.

What actually shipped

All of the HTML generation lives in one Python module that emits static HTML. I grouped the report into six tab panels (Overview, Markets, Macro, Opportunities, Signals, Crisis), added a small helper for consistent <details> / <summary> blocks, and rewired Opportunities from _opp_card() to _opp_row() so each idea is a single scannable row that expands when you want the thesis.

Then I pushed, let CI run, and watched Pages deploy. Green build, live URL, done.

The meta-lesson

The modern default is “reach for a framework.” Sometimes that is correct. But for a content-first, CI-generated surface where the hard work is data and judgment, static HTML plus a little JS is not a compromise. It is a product decision: fewer moving parts between the analyst (me) and the reader (also often me — but now on mobile, before coffee).

If you are sitting on a “too long” dashboard, try the monster-section audit before you try the framework migration. You might discover you only needed tabs and self-respect.
