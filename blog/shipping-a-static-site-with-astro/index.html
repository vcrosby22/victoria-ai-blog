Shipping a Static Site With Astro in 2026

Why I chose Astro for this blog, how the content collection system works, and the decisions behind a Markdown-first publishing workflow.

#astro#static-sites#architecture#markdown

This blog runs on Astro. Here’s why, and what the setup looks like.

Why Astro

I evaluated Hugo, Next.js, Eleventy, and Astro. The deciding factors:

  1. Markdown-first with type safety — Astro’s content collections let you define a schema for your frontmatter. Posts that don’t match the schema fail at build time, not in production.
  2. Zero JavaScript by default — pages ship as pure HTML and CSS unless you explicitly opt into client-side JS. Fast is the default.
  3. Modern DX — hot reload, TypeScript, component-based layouts. It feels like a modern framework, not a documentation tool.
  4. Room to grow — if I ever want interactive components in posts (charts, demos), Astro supports partial hydration with React, Svelte, or Vue.

Content collections

Every post is a Markdown file with typed frontmatter:

---
title: "Post Title"
description: "A description"
pubDate: 2026-03-21
category: "ai"
tags: ["agents", "cursor"]
---

The schema is defined once in content.config.ts, and Astro validates every post against it. Categories are an enum — you can’t invent a new one without updating the schema. This prevents drift.

The publish workflow

  1. Write a .md file in src/content/blog/
  2. Run npm run dev to preview locally
  3. Build and deploy

No CMS, no database, no API calls at build time. The content is in the repo, versioned with git, and editable with any text editor or AI agent.

What I’d do differently next time

Nothing yet — this is day one. But I expect the first thing I’ll want is an RSS feed (already configured) and eventually tag-based filtering on the blog index.

If you’re choosing a static site generator in 2026, I’d recommend Astro unless you have a specific reason to choose something else.
